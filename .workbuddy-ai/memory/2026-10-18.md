## Bots: what they DO, and why they're tied to a human (owner asked, measured)

Doc: `library/development/ANALYSIS-2026-10-18-bots-use-cases-and-ownership.md`.

- **★ I had to correct my own diagram.** I drew "person leaves → bot stops working" as inherent to delegation.
  Measured: **nobody hard-deletes a bot with its owner.** Zulip *deactivates* (row survives, renamed
  "Deactivated bot"); Multica *refuses to delete the owner* (`owner_id` FK, no ON DELETE → NO ACTION);
  Buzz leaves it (owner link immutable, first-mint-wins); Slack's bot is app-level.
- **Zulip's owner link is a FLOOR, not a leash:** `lib/streams.py:632-637` + `:712-717` check the bot's OWN
  membership first, then fall back to the owner's — "Bots can send to any stream their owner can."
- **Zulip's deactivation cascade is deliberate policy, not cascade-by-accident** (`actions/users.py:470-494`):
  bots first "so a failure partway cannot result in only the user being deactivated"; reason = "same policies
  as the user who created them" (spam/abuse).
- **Multica's strongest owner reason = data access:** `originator == agent.owner_id` gate so an agent never
  gets another user's Composio session (migration 129). And `originator_user_id` is **nullable** — "NULL when
  no human is in the chain (autopilot, system-driven)". So first-class bots are explicitly supported there.
- **Zulip's bot TAXONOMY is a capability taxonomy** (`models/users.py:451-478`): generic / incoming webhook
  ("can't be used to read messages") / outgoing webhook / embedded. Type chosen at creation.
- **7 end-user jobs** (privilege ladder): messenger · responder · helper-in-room · private assistant ·
  colleague · worker-on-ticket · delegate. Ours = **colleague** (needs own membership; human only to start).
- **Reframed decision: 3 independent settings**, not A/B — reach (own/owner-floor) · on-owner-departure
  (deactivate/leave/block) · human-per-request (always/only-to-start). Recommended: own + owner-floor,
  deactivate-never-delete, only-to-start.
