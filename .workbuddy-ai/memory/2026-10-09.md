## OWNER RULING — the core object set becomes a SETTING, not hardcoded (SD-2b)

**Owner's ruling (verbatim intent):** *"we follow your recommendations concerning that. However, analyze if
we can do this as a manageable matter instead of hardcoded. Give the superadmin the right and functionality

**Answer: yes — and the platform already contains the exact pattern.** `SD-3` did this one turn earlier for
the tier mapping, after the same owner instruction (*"let's not make it hardcoded but a setting a superadmin
can change"*). The template is `shared/src/lib/request-outcome/tier-source.ts`: **seed + strict parser +

(`getValue`/`setValue`/`restoreDefaults`/`invalidate`) already built. **No new table, no migration.**

**The split (and the owner's wording already respects it):**
- **SETTING (Ring 2):** the object→tier map; the default tier for an unmapped object; the system-column set;
  the reserved-entity-type set. A superadmin edits these from the UI.
- **CODE (Ring 1, `CORE-BOUNDARY.md` §2):** the *rule* that a `core` object cannot be deleted or
  restructured; the four tier names; the fail-closed parser. *A setting can move an object BETWEEN tiers;
  it can never DELETE the tiers.*

**The four tiers:** `core` (Ring 1) · `platform_release` (protected from users) · `tenant_structural` (S2
gate + SD-4 grammar) · `tenant_data` (ordinary RBAC). My earlier Tier-1 rec = the seed's `core` rows;
Tier-2 = the seed's `platform_release`; absence = the default `tenant_structural`.

**It corrected a real defect in my first recommendation:** hardcoding the ~25 tables would have meant a
**deploy to protect a table the superadmin just created** — wrong for a customizable platform.

**Honest note:** `SD-3`'s own setting has **no UI yet** (measured: only `configs/cli.ts` writes it). So the
manage screen for the core set folds into **`SD-5`** (one per-object grid, two settings), not a second UI.
