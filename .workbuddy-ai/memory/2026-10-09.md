## The owner's core-object ruling — the DATABASE-side backbone (proposal written)

**Owner's point (verbatim intent):** *"it is important to look at core architecture from the database side
as well (which is even more important). In a platform where users can customize database, there are
tables/columns/relationships that should not be editable because they are the backbone of the schema and
editing it can crash the system."*

**The correction I had to make (and it matters):** there are **two axes**, and `SD-2` built only one.

| Axis | Harm | Vector | Guard |
|---|---|---|---|
| **A — row-level** | an object is **deleted** (the `superadmin` role) | `DELETE` on a row | **`SD-2` — BUILT** |
| **B — structural** | the **schema backbone is changed** (table dropped, column removed/re-typed, relation broken) | customization UI / S2 gate / Hermes-proposed change | **NOT built** — the owner is asking about this one |

**Measured (live PG 17, `open-mercato`):** 143 tables, 112 ORM entity definitions; populated starter data:
tenants 1, organizations 1, users 3, roles 3, role_acls 3, user_roles 3.

**Three prior-art lists already exist, none answering "may this be changed at all":**
1. `shared/src/lib/entities/system-entities.ts` — 7 reserved entity types → **UI selectability only**.
2. `core/.../entities/data/guards.ts:69` — 7 `RESERVED_RECORD_KEYS` → **custom-field column collision**.
3. `shared/src/lib/data/engine.ts:165` (`isOrmBackedSystemEntityId`) → **doc-storage routing** (the
   deepest existing seam; the natural one to extend).

**The measured hole:** a custom field can be attached to a system table — the only block is the 7-id
selectability list, and `users`, `roles`, `tenants`, `sessions` are **not in it**. Nothing covers a DROP or a
broken FK.

**Recommendation written up in `library/development/DECISION-core-object-set.md`:**
- **Tier 1 (core now, ~25 tables):** tenants, organizations(+edges), users/user_roles/user_acls,
  roles/role_acls, sessions/password_resets/api_keys, action_logs/access_logs, the customization substrate
  (custom_entities*, custom_field_*), the index/search tables, module_configs, the migration ledger.
- **Tier 2 (core by default, releasable by a platform release):** authority_*, feature_toggles, webhooks,
  scheduled_jobs, workflow_definitions, record_locks, encryption_maps, perspectives/sidebar_variants.
- **Tier 3 (NOT core):** business data + packs (customers, catalog, sales, wms, staff…) — governed by `SD-1` + `SD-4`.
- **Columns/relations rule:** for Tier-1 tables, system columns (`id`, `tenant_id`, `organization_id`,
  `created_at`, `updated_at`, `deleted_at`) un-removable/un-re-typable; FKs fixed.
- **Sizing:** widen the registry (small) + widen `isSystemEntitySelectable` (small) **now**; the structural
  `MutationGuard` (medium) scheduled with `SD-4` (S5: one engine, not two).

## OWNER RULING — the core object set becomes a SETTING, not hardcoded (SD-2b)

**Owner's ruling (verbatim intent):** *"we follow your recommendations concerning that. However, analyze if
we can do this as a manageable matter instead of hardcoded. Give the superadmin the right and functionality
to identify which table/column/function belongs to which tier… your recommendations become **default
settings**, not hardcoded architecture."*

**Answer: yes — and the platform already contains the exact pattern.** `SD-3` did this one turn earlier for
the tier mapping, after the same owner instruction (*"let's not make it hardcoded but a setting a superadmin
can change"*). The template is `shared/src/lib/request-outcome/tier-source.ts`: **seed + strict parser +
pure decision + fail-closed async read**, stored in `module_configs`, with `ModuleConfigService`
(`getValue`/`setValue`/`restoreDefaults`/`invalidate`) already built. **No new table, no migration.**

**The split (and the owner's wording already respects it):**
- **SETTING (Ring 2):** the object→tier map; the default tier for an unmapped object; the system-column set;
  the reserved-entity-type set. A superadmin edits these from the UI.
- **CODE (Ring 1, `CORE-BOUNDARY.md` §2):** the *rule* that a `core` object cannot be deleted or
  restructured; the four tier names; the fail-closed parser. *A setting can move an object BETWEEN tiers;
  it can never DELETE the tiers.*

**The four tiers:** `core` (Ring 1) · `platform_release` (protected from users) · `tenant_structural` (S2
gate + SD-4 grammar) · `tenant_data` (ordinary RBAC). My earlier Tier-1 rec = the seed's `core` rows;
Tier-2 = the seed's `platform_release`; absence = the default `tenant_structural`.

**It corrected a real defect in my first recommendation:** hardcoding the ~25 tables would have meant a
**deploy to protect a table the superadmin just created** — wrong for a customizable platform.

**Honest note:** `SD-3`'s own setting has **no UI yet** (measured: only `configs/cli.ts` writes it). So the
manage screen for the core set folds into **`SD-5`** (one per-object grid, two settings), not a second UI.

**Tracked:** owner ruling closed in `NEEDS-YOU.md` item 15; the build is **`SD-2b`** (BACKLOG + BUILD-ORDER
§7b); CC-31(b) updated (ruled); the `★ ACTIVE TASK` box now posts **`SD-2b`** ahead of `SD-4`/`SD-5`
(because the structural grammar READS the tier map this setting stores). Design:
`DECISION-core-object-set-as-settings.md`.

## SD-4 SLICE B BUILT — the actor axis (S12)

**What shipped.** An **optional** `actorKind?: PrincipalKind` now rides the guard engine:
`MutationGuardInput` + `MutationGuardAfterInput` (`mutation-guard-registry.ts`), `RouteMutationGuardAuth`
(`route-mutation-guard.ts`), threaded into **both** the validate input and the `afterSuccess` input of
`runRouteMutationGuards`, and set by the **eight** guard-input builders (`factory.ts` ×7 +
`beginEntitiesMutationGuard`). The structural guard **reads** it: `structuralGuardRefusal(payload, op, settings,
actorKind)` names a machine actor in its refusal, so the field is a real reader — not the decoration the rules
forbid.

**The derivation, and the regression the hostile critic caught (HIGH — fixed pre-commit).** My first draft read
`auth.principal?.kind` **directly**, reasoning "every real path populates `principal`". The critic proved that
**false**: the in-process AI runner ([`ai-api-operation-runner.ts`](workspace/starting-kit/packages/ai-assistant/src/modules/ai_assistant/lib/ai-api-operation-runner.ts)
`buildAuthEnvelope`) hands routes a *trusted envelope* whose `AuthContext` carries `sub:'ai_worker:<id>'` and
**no `principal` field**, and `resolveAuthFromRequestDetailed` returns it **verbatim** (no
`withResolvedPrincipal`). So the one path S12 exists to bound — a machine — was labelled *unknown*. **Fix:**
resolve as `auth.principal?.kind ?? derivePrincipal(auth)?.kind`, importing `derivePrincipal` from
**`auth/principal`** (the pure module that owns the subject encoding, **mocked nowhere**: `grep` count = 0) —
**not** `auth/server` (mocked wholesale by every route test). Pinned by **three** derivation tests
(trusted-envelope `ai_worker`, `service` api-key subject, bare `human`) that go **RED** on the direct read
(mutation **M6**). *The critic earned its keep twice over.*

**The second HIGH the critic caught — an over-stated claim (docs corrected, code unchanged).** The axis today
changes only the refusal **message**, never the decision (`ok`/`status`/allow-vs-refuse are actor-invariant).
That is **correct for Slice B's scope** — make the axis *reach* the guard so the per-actor **grammar** (Slice C)
can use it — but it must not be sold as "a structural decision already differs for a person and a machine". The
headline is corrected in `PLAN-SD-4.md` §5/§9, `JOURNAL.md`, `BACKLOG.md`, `BUILD-ORDER.md` and
`platform_points.md` S12.

**The critic's other findings.** MEDIUM — `messages`, `configs.cache`, `communication_channels`, `staff`,
`payment_gateways`, `integrations`, `sales/quotes/*` build guard inputs without `actorKind` (harmless today;
scheduled as **CC-36**). LOW — `guards.sd4.test.ts` proved the record-write narrowing with
`'entities.custom_entity_record'`, a string **no production route emits** (real: `'entities.record'`); **fixed**,
