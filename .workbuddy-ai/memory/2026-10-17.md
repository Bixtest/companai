### T-32 — a v7 record id no longer hides a record's lock (`13c6206f`)

The hole (audit A1-09): `readRecordId` (`interceptors.ts:89`) accepted only RFC-4122 v1–v5 ids —
version nibble `[1-5]`, variant nibble `[89ab]` — so a valid v7 id failed the pattern, reached the
resolver as `recordId: null`, and `resourceCeilingFor` (`authorityEnforcementService.ts:335`)
early-returned on `!recordId`: **the lock was never looked up**. The command gate is the **only
production caller that threads a recordId** (`refusalFor` at `rbacService.ts:595` calls `decideFor`
with no options; the AI tool path threads only `onBehalfOfUserId`).

**The fix went beyond the recorded one, by name (rule 13):** the triage recorded `[1-5]` →
`[0-9a-f]`; the variant nibble is the same class of over-strictness, so the pattern is now **shape
only** — `/^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$/i`, the exact shape
`sync-run-service.ts:7` and `grantChecks.ts:46` already use (`crud/ids.ts:5` relaxes with `[1-8]`).
Version and variant are properties of the **generator**, not the record.

Proof: 7 tests in `authority-command-gate.record-id.test.ts` driving the real gate + the real
service with a stub lock reader; **the decisive assertion is that the lookup happened at all** —
`stateFor` called with the record's real id, after which a restricted record named by a v7 id is
**held** at A2. 4 mutations run for real (M1 restore the pre-fix pattern → hole ×2 + uppercase +
