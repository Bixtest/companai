`sync-run-service.ts:7` and `grantChecks.ts:46` already use (`crud/ids.ts:5` relaxes with `[1-8]`).
Version and variant are properties of the **generator**, not the record.

Proof: 7 tests in `authority-command-gate.record-id.test.ts` driving the real gate + the real

### ★ FIRST APPLICATION OF THE RULE — and it overturned the plan

`SR-02` slice 2 (the retire guard). Plan §4.2 said: *"a runtime that a live agent binding names must not be
retirable — the `ON DELETE RESTRICT` promise."* **That had the donor backwards.**

Measured in `multica-main`:
- `004_agent_runtime_loop.up.sql:73` **does** declare `agent.runtime_id … ON DELETE RESTRICT`; `:86`
  declares `agent_task_queue.runtime_id … ON DELETE CASCADE`.
- But `251_agent_runtime_unbind.up.sql` **drops `NOT NULL` on both** and says why: *"Retiring a laptop is
  an ordinary action; losing the agents configured on it is not an ordinary consequence."* The unbind is an
  **application-layer UPDATE inside the delete transaction**; the FK survives only as a backstop
  (*"No new foreign keys or cascading actions are introduced"* — their repository rule).
- So the promise is **"neither destroy the agent nor strand it silently"**, not "refuse".

**Five mechanisms harvested** (`server/internal/handler/runtime.go`):
1. **Two doors, not a flag** — `DeleteAgentRuntime` (:991) refuses 409; `UnbindAgentsAndDeleteRuntime`
   (:1200) is a separate endpoint.
2. **The refusal carries the dependant list** — *"saves a second round-trip when the user clicked Delete
   from a stale list page."*
3. **Confirmation over a SET, re-verified server-side** — `expected_active_agent_ids`; mismatch →
   `runtime_delete_plan_changed`. Closes the dialog-open→confirm race.
4. **Check → lock → re-check (TOCTOU)** — `LockAgentRuntime` takes `FOR UPDATE`, which conflicts with the
   FK's `FOR KEY SHARE`. **Without this the guard is decorative under concurrency** — every sequential test
   still passes.
5. **The invariant moves to run time** — `CHECK (runtime_id IS NOT NULL OR completed_at IS NOT NULL) NOT
   VALID`, expressed with `completed_at` not a status list *"because naming enumerable status values in a
   constraint would force a migration for each new status"* → a future non-terminal status **fails closed**.
Also: `251`'s `down()` **refuses to delete data to make itself succeed** and prints the queries instead.
