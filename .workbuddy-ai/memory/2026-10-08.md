## `S-02` — the Hermes tool door: wire the authority resolver as the AI tool door's enforcement point

**Task (from the `★ ACTIVE TASK` box, posted 2026-10-07).** Service-map §4.4(b): *"an agent acts on
behalf of a person, and its authority is the intersection of its own and that person's, decided inside
the single decider. This is where a Hermes tool call is actually authorized. A named warning from the
source study: fail closed, or do not ship the switch."*

**Fact-check (step 4) — the honest boundary.** S-02 was **not** "build the resolver" (it exists:
`shared/src/lib/authority/decision.ts`, `resolveDecision`) and **not** "supply five inputs" (the existing
`AuthorityEnforcementService.decideFor(subject, feature, scope, {onBehalfOfUserId, recordId})` already

**What was built (code repo).**
- `packages/ai-assistant/src/modules/ai_assistant/lib/tool-authority.ts` (NEW) —
  `checkToolAuthority(toolName, requiredFeatures, context)`. Asks the **same** `AuthorityEnforcementService`
  the command gate asks, same `onBehalfOfUserId`, reads the same `Decision`. Runs **after** RBAC (narrow-only
  — invariant **I4**); **fails closed** when the resolver is unreachable; `off`/`shadow` never refuse;
  undescribed capability = coverage gap, not refusal.

- `lib/pending-action-executor.ts` — a **confirm-path** gate between the `executing` transition and the
  handler; non-permit → `failed` (`authority_refused` / `authority_held`). (State machine:
  `pending→confirmed→executing→failed` — `pending→failed` is illegal.)
- `McpToolContext.onBehalfOfUserId` added and populated at **every** door that resolves a machine subject
  (`auth.ts`: `apiKey.sessionUserId ?? apiKey.createdBy ?? null`; `mcp-server` / `mcp-dev-server` /
  `in-process-client`); `http-server` deliberately unchanged (it puts a real user id in `userId`).

  (`userId`). Deriving it was my own first bug, caught by the intersection test.

## `SD-1` — the S2 permissions gate: the decision core is built; the enforcement half is NOT. **PARTIAL.**

**Fact-check (step 4).** SD-1 is not "build the resolver" and not "add a table" — it is **the permissions
question made unskippable**. Measured: **no permission catalogue exists** (grep for
`permissionCatalogue`/`permission_record` → 0 files). Permissions are `features_json` string arrays on
`RoleAcl`/`UserAcl` (`auth/data/entities.ts:272/307`); the check is a pure string match
(`shared/src/security/features.ts`). Two things DO exist and were reused (S5 — one engine): the
**capability registry** (`shared/src/lib/capabilities/registry.ts`, declared descriptors from each module's
`acl.ts`) and the **per-entity synthesized records** (`entities/lib/recordFeatures.ts` →
`entities.records.<entityId>.view|manage`, aggregated by `auth/api/features.ts` +
`restrictedEntityFeatures.ts`). The change path is the **MutationGuard socket**
(`beginEntitiesMutationGuard` → `runRouteMutationGuards` → `runMutationGuards`).

**The constraint that shaped the design.** DB-backed code is tested against a **mocked EntityManager**, so
a migration is **unprovable on this host** (`user-function/document.ts:22-28` states the same reasoning).
So the catalogue is a **typed `shared` service**, not a new table — like the metadata registry.

**What was built.** `shared/src/lib/permissions/catalogue.ts` (surfaces + the two blocks each yields: data
`view`/`manage` + structural `structure`; `declareSurfaces`/`recordSurface`/`permissionRecordsFor`/
`hydrateCatalogueFromFeatures`) and `structure-change-gate.ts` (`evaluateStructureChange` → `decided |
defaulted | refused`, pure, fail-closed: `no_surface` / `malformed_surface_id` /
`unrecognised_surface_kind` / `empty_decision`; `DEFAULT_GRANT_ROLE='superadmin'`). Hook: two
`MutationGuard`s on `entities.field_definition` / `entities.entity` `create` in `entities/data/guards.ts`,
registered in the exported `guards` array.

**Verification.** 37 new tests. **8 mutations RED-then-GREEN**, each restore **md5-verified byte-identical**
(bytes I/O — the LF→CRLF trap bit a scripted restore twice, caught both times by the md5 check).
`shared` **197 suites / 2327**; `core` **618 suites / 5332**; typecheck **0** (both packages).

**HOSTILE-CRITIC PASS (separate agent) FOUND FIVE REAL DEFECTS.** All fixed or named:
1. **`featurePrefix` fail-open** — `permissionRecordsFor` validated `surface.id` but not the prefix, so an
   unreadable prefix produced unreadable ids and the gate said `defaulted`. **FIXED** (+ tests, + M7/M8).
2. **The batch create path is ungated** — `api/definitions.batch.ts` creates NEW columns under
   `operation:'custom'` → mapped to `'update'`, so a create-only guard never sees them. **NAMED.**
3. **Module-install + CLI create definitions with no guard.** **NAMED.**
4. **The hook blocks nothing on its routes** — the routes' zod schemas guarantee `entityId`/`key`, so the
   gate always defaults; and **nothing writes the records**. **This is the headline: the item is PARTIAL.**
5. **Dangling `PLAN-SD-1.md §10` reference.** **FIXED** (the section now exists).
The critic also showed the gate's records-empty check was **dead code**; defect 1's fix made it reachable.

**Why it is PARTIAL (the honest headline).** S2 says a new structure must not land until permissions are
decided **and the records created**. The gate *decides* and the hook *fails closed*, but **no call site
persists the default into `role_acls.features_json`** — so on the HTTP routes the gate enumerates and
passes without changing the ACL. **A gate that decides but does not record is not yet a gate.** Not ticked
in JOURNAL/platform_points.

**Next slice (in order).** (1) write the records (apply `defaulted` to the tenant's superadmin role via the
existing store); (2) close the batch create path; (3) name or gate the module-install/CLI paths;
(4) field-type-change detection (needs the before-state). Plan: `library/development/PLAN-SD-1.md` (§9 the
critic, §10 the limits).

"the hook is a pass-through" truth that the tests could not see (the tests proved the *guard*, not the
