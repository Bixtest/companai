## P2-4 design finding — the tool-selection question (measured before any code)

The owner asked: *"if 'tool' means what an agent uses, and different agents use different tools,
shouldn't the tool be selected based on the agent type?"* Measured in the code repo
(`packages/ai-assistant/src/modules/ai_assistant/`), 2026-10-13:

1. **Agent tool selection ALREADY EXISTS on the platform's own runtime.** `AiAgentDefinition`
   (`lib/ai-agent-definition.ts:290`) carries `allowedTools: string[]` + `requiredFeatures` +
   mutation policy. `lib/agent-tools.ts::resolveAiAgentTools({agentId, authContext, …})` builds the
   model's tool map from `agent.allowedTools`, **narrowed** by any `ai_agent_bindings` row
   (`boundScope`, CC-55 — a binding may never ADD a tool, `B3'a`), then gates every tool through
   `checkAgentPolicy` (features · execution mode · mutation policy). The model never sees a tool its
   agent did not declare. So the answer is "per agent" (finer than per type); the five kinds
   (`ce.ts:54` — personal · role · context · independent · system) are an ownership concept only.
2. **The door is agent-blind.** `resolveToolCall(call: AiRuntimeToolCall, capabilityGrant: string)`
   (`lib/ai-runtime-port.ts:354`) — no agentId, no whitelist. But the ENVELOPE carries the real
   `agentId` (`lib/ai-runtime-port.ts:78`), and every adapter stores its runs from `startRun`, so
   the agent identity is available at the call site via the run (the stream observes
   `tool.start {tool_id}` → the call is correlatable to its run).
3. **The "capability grant" is a LABEL, not an authority.** Both chat routes mint it synthetically:
   `capabilityGrantId: \`chat-turn:${auth.sub}:${runId}\`` (`api/ai/chat/route.ts:791`,
   `api/chat/route.ts:531`). Nothing resolves it. It proves a call belongs to a chat turn; it does
   not prove the call is allowed. ⇒ the plan's P2-4 promise "re-authorized at execution time"
   cannot be fully honest until grants resolve — a NEW open item (register as `CC-77` if kept).
4. **The four tool packs are orphans** — zero references to `businessIrAiTools` etc. outside
   `ai-tools/` itself (only their own tests). P2-4 is the first wiring of any pack to anything.

**The risk if P2-4 checks the grant only:** the engine raises a call, the label matches, the
platform executes — for an agent whose `allowedTools` never included that tool. The model ends up
choosing its own tools = exactly what the architecture §8 forbids ("the runtime may narrow the
grant, never widen it"). **Latent, not live:** all three adapters report `resolveToolCall: false`,
so no caller can reach it today — P2-4 is the row that would make it live.

**Design fork handed to the owner (rule 11), ranked:**
1. **(RECOMMENDED) Two gates at the door:** the agent's declared tool list (from the run's
   `agentId`, via the registry) AND the grant. Rule: *admission decides with the person's
   permissions (where they live), the door enforces only what admission allowed.* The door cannot
   re-derive features — the envelope deliberately does not carry them — so the features-gated half
   stays at admission (`resolveAiAgentTools`), which already exists. Open sub-question: the
   binding-narrowed (effective) list is not on the envelope — either admission records it per run
   or the door enforces the declared list only (smaller residual: an agent-declared tool a binding
   removed).
2. Grant-only as the plan literally says — smallest, but ships the widening live + a callback
   (the CC-74 "register it and remember" pattern again).
3. Defer the agent gate to a later sub-row — splits one code path across rows (rule 10d tension).

**Nothing coded.** Requirement for P2-4 must be re-written BEFORE any code (rule 3) once the owner
picks the shape. Business-IR confirmed as the first tool ("proceed based on your recommendation").
