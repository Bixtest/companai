buzz Study — Batch 00: the pin, the method, and what this study is#

Folder: library/architecture/buzz-forensics/ · Status: OPEN — begun 2026-10-16 This is a clean forensic study, run the same way as hermes-forensics/, paperclip-forensics/, crewai-forensics/, multica-forensics/, gastown-forensics/ and n8n-forensics/. It reads ONE source tree, measures it, and verifies every load-bearing claim against the source code. Nothing from any earlier study is reused, referenced, or assumed — buzz is read on its own terms.

Why this platform is seventh. The owner's ruling was "one platform at a time": Hermes, Paperclip, CrewAI, Multica, Gas Town and n8n are closed. buzz is seventh — the owner named it with one word, "buzz", following the workshop's own order. It is the first platform in this study that is not primarily a workflow tool or an agent orchestrator, but a communication substrate: a team workspace built on a public protocol (Nostr), where a message, a reaction, a workflow step, a canvas edit, a code review approval and a git event are all the same kind of object — a signed event in one log. Six platforms have now been measured against the three poles; buzz is the first whose stated premise is that the workspace is the event log, and the first whose tenant boundary is proven with formal methods rather than asserted in prose.

The owner's directive carried into this study (from the n8n brief, still in force): identify what fits the vision and what could be taken further. Per the method, the batches stay comparison-free — the "take it further" notes are observations in the synthesis, and the decisions stay the owner's at the mapping pass.

1.1 The identity limit (stated, not glossed)#

There is no .git, so the exact upstream commit cannot be read from the tree. What is readable is the latest changelog release heading — v0.5.28 — and, unusually, the changelog entries carry the upstream commit SHAs and PR numbers inline (… ([#8186](https://github.com/block/buzz/pull/8186)) ([8f66f705…](https://github.com/block/buzz/commit/8f66f705…))). The tree is richer in provenance than n8n's was: 445,253 bytes of changelog with real commit hashes. Any claim here about "the latest buzz" is a claim about this extract, at v0.5.28.

⚠️ A naming hazard a later reader must be told, because it will confuse them. The product is called buzz, but the code speaks three other names:

  • the Cargo workspace repository field points at https://github.com/block/sprout (a former name);
  • the root package.json names the JS workspace buzz-workspace, and one crate is sprig (there is a whole Dockerfile.sprig and a [profile.sprig] release profile);
  • the zip is buzz-main.zip and every crate is prefixed buzz-.

So buzz · sprout · sprig all appear in the same tree and mean the same product at different times. This is the study's first measured rename; it is recorded here so no batch mistakes "sprout" or "sprig" for a second product or a dependency.

1.2 Where the extract lives, and why it is where n8n is not#

Unlike n8n (which had to be extracted to C:\n8n because its longest paths exceeded Windows' 260-char MAX_PATH), buzz extracted cleanly into the conventional location platforms/_extracted/buzz-main. The measured reason: buzz's longest path is 118 characters — far under the limit. The conventional location is correct for this study; nothing special is required to reproduce it.

Two facts stand out immediately, and both are hazards of the same kind as earlier studies:

  • Rust is the product. .rs is 27.6 MB against .ts+.tsx at 15.6 MB — the server was chosen deliberately and is the majority language by bytes. A reader who assumes "another TS monorepo" (as n8n was) will misread this study.
  • .png is 22.2 MB — nearly as much as all the Rust. The screenshots in docs/assets/screenshots/ are a large fraction of the repo by bytes. A "repo size" reading here is ~22 % pictures, and a byte-share table that ignores this will overstate the code's share of the download.

2.3 The test ratio — measured before any finding was written, and corrected#

This is the study's most important measurement, because the first reading of it was wrong.

  • By filename the count says 45 of 537 .rs files in crates/ are tests — an 8.4 % share by file, or 0.3 % if you only count files literally named *_test.rs. That is what a naive pass finds.

  • By lines — counting tests/, benches/ and examples/ directories as test, and splitting each inline #[cfg(test)] module out of its file — the truth is:

    crates/ = 502,880 Rust lines = 194,631 product + 308,249 test → a 61.3 % test share.

The filename count and the line count differ by a factor of ~7 by file and ~200× on the "0.3 %" reading — and the real answer is the HIGHEST test share in the entire study (Gas Town 46 %, Multica 48 %, n8n 32.8 %). The reason is structural: buzz writes its tests inline in the same file, after a #[cfg(test)] marker, so the file is a product file and the majority of its lines are test. Any "lines of Rust" figure in this study is 61.3 % test code unless it says otherwise — and this pin says so once, here, so every later batch can cite it.

(The correction is recorded rather than quietly fixed, because it is rule 1 in action: the first number was a filename artifact, the code was the authority, and the disagreement is now on the record.)

2.7 The licence — Apache-2.0, and it is NOT a gate#

LICENSE is the Apache License, Version 2.0 in full; Cargo.toml declares license = "Apache-2.0". There is no .ee-style carve-out, no "Sustainable Use" clause, no enterprise directory. This is the study's first genuinely open-source platform — and it is a sharp contrast with n8n (§2.5 of that pin: fair-code, .ee unlicensed, ai-workflow-builder.ee gated). Recorded because it changes one thing materially: unlike n8n, where the licence constrains every "can we take this?" question, here the licence does not. The constraint is architectural, not legal — which is exactly why the study still reads the code rather than assuming "open source means usable".

3. The method (how every batch is produced)#

The method is inherited verbatim from the six closed studies (rules 1–10), with the pole frame (§3.1) and the additive-across-studies rule (§3.2) as before.

  1. Docs are claims; code is the authority. Every load-bearing statement is checked against the source. Where they disagree, the code wins and the disagreement is recorded.
  2. Every number is measured at the time of writing, never carried from memory or an older document.
  3. Claims carry their evidence: a line resting on code cites the file and line it was read at.
  4. Two value questions per capability: Q1 · USER VALUE (how it serves a person using the platform) and Q2 · VISION VALUE (how it serves the AI-first business & resources planner vision, incl. versatility and integratability).
  5. No comparison to our own platform inside the batches. The cross-platform mapping is a separate later pass.
  6. Every capability is named, including ones we will not use. Nothing is silently dropped.
  7. Findings are additive and never overwrite history.
  8. Plain words — every capability gets a one-sentence plain gloss before any detail.
  9. THE POLE FRAME. Every finding is tagged P1 / P2 / P3 / PX-W / PX-F / PZ.
  10. The retirement rule. Before reusing any setting/key/module named in an older document or another platform's doc, search this platform's config/CHANGELOG for a retirement entry. buzz has a 445 KB changelog with inline commit hashes, and it renames its own product (§1.1) — so the retirement surface here is unusually active.

Tag Pole The owner's words (abridged)
P1 The aissistant (the AI user / agent) versatile, integratable, rich featured architecture in itself, deployable in different contexts (workspaces, automations, later the studio)
P2 The workspace highly functional, versatile, integratable, rich featured, adaptable to the mix of current and future features, use-cases and needs
P3 Automations where agents work on assigned tasks, assign tasks, etc. Paperclip is a blueprint

Plus one escape hatch (PZ): "any other findings you identify there that can fit our vision, project, architecture, or a potential use case or added value for the end user." Tagged PZ with a one-line reason for keeping them.

3.2 Additive across studies, like rule 7 within a study#

This study does not rewrite the six closed studies. Where a buzz finding confirms, contradicts or extends an earlier finding, it is recorded as a cross-study note naming the earlier batch — so a reader can trace both directions. Cross-study notes are observations, never decisions.

4. The batch plan (each documented as it is completed)#

Findings are organised per pole, one file per pole, plus an overview and a synthesis. buzz's pole weighting is expected to differ from all six earlier studies — P2 (the workspace/tenancy boundary) and P1 (agents-as-members) are expected to be the strongest, P3 possibly the thinnest — but the structure is identical so the later mapping is a per-pole join.

5. The owner's directive for this study#

Carried forward from the n8n brief, unchanged:

  1. What fits the vision — answered per capability in the batches and ranked in batch 07.
  2. What could be taken further — recorded as observations in batch 07 §7, never as decisions.

The method's discipline still holds inside the batches: rule 5 (no comparison to our own platform) applies to batches 01–06. The synthesis (§7) may name a mechanism as extensible — e.g. "this pattern would allow X" — but it must stop at the observation. The mapping pass and the owner decide.

And — unlike n8n — there is no licence gate to carry. Apache-2.0 (§2.7). The discipline that replaces it is the study's own: read every claim against the code, because open source means readable, not correct.

6. Ground rules restated as a checklist the reader can hold this study to#

  • Is the claim measured, or remembered? → must be measured.
  • Does the line rest on a doc, or on code? → code, always.
  • If doc and code disagree, is the disagreement recorded? → must be.
  • Is every capability named, including the ones we will not use? → must be.
  • Is every finding tagged with its pole (P1/P2/P3/PX-W/PX-F/PZ)? → must be.
  • Are the two value questions answered in the owner's words? → yes, per capability.
  • Is there any comparison to our own platform in a batch? → must be none; that is the later mapping pass.
  • Before reusing an older-doc setting, was the retirement rule run (rule 10)? → must be — and note that this platform renames itself (buzz/sprout/sprig, §1.1), so names are a retirement surface.
  • Does the line count say whether it includes tests? → with 61.3 % of crates/ Rust lines being tests, every count in this study states its basis.
  • Is a formal-methods file being read as a guarantee? → no: it is a model to verify against the code (rule 1).
