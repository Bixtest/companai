3. The method (how every batch is produced)#

The method is inherited verbatim from the Hermes study, because it earned its keep — plus one addition (the pole frame) that this stage of the project requires.

  1. Docs are claims; code is the authority. Every load-bearing statement a doc makes is checked against the TypeScript source. Where they disagree, the code wins and the disagreement is recorded.
  2. Every number is measured at the time of writing, never carried from memory or from an older document.
  3. Claims carry their evidence: a line resting on code cites the file and line it was read at.
  4. Two value questions per capability, per the owner's standing instruction:
    • Q1 · USER VALUE — how does this serve a real use case for a person using the platform?
    • Q2 · VISION VALUE — how does this serve the vision of an AI-first business & resources planner, now and long-run, including versatility and integratability?
  5. No comparison to our own platform inside the batches. Understanding first; the cross-platform mapping is a separate later pass (the owner's step: "we start mapping each pole findings across the platforms with what we have already in mercato").
  6. Every capability is named, including ones we will not use. Nothing is silently dropped.
  7. Findings are additive and never overwrite history (rule 7 from Hermes; see also §3.2 for the cross-study form).
  8. Plain words — every capability gets a one-sentence plain gloss before any detail.
  9. THE POLE FRAME (new to this study). Every capability finding is tagged with which of the three poles it informs — see §3.1 — so the later cross-platform mapping is a per-pole join rather than a re-read of nine studies.
  10. The retirement rule (C13-14, inherited). Before reusing any setting, key, feature or module named in an older document or another platform's doc, search that platform's migrations/config for a retirement entry. A silently-removed feature is the most valuable kind of finding (Hermes Taught us this with security.tirith_*).

3.1 The pole frame — the three poles, defined once#

The owner defined three poles plus two cross-cutting concerns. Every batch tags its findings against them:

Tag Pole The owner's words (abridged)
P1 The aissistant (the AI user / agent) engineer the agent to be versatile, integratable, and rich featured architecture in itself, deployable in different contexts and needs (workspaces, automations, later the studio)
P2 The workspace highly functional, versatile, integratable, rich featured architecture that adapts and provides the compatibility of the mix of current and future features, use-cases and needs
P3 Automations where agents work on assigned tasks, assign tasks, etc. Paperclip is a blueprint for that
PX-W Widgets architecture cross-cutting: the composable UI surface
PX-F Frontend wiring & construction cross-cutting: how the surface is built and wired

Plus one escape hatch, per the owner: "add any other findings you identify there that can fit our vision, project, architecture, or a potential use case or added value for the end user." Those are tagged PZ (out-of-pole findings) with a one-line reason for keeping them.

3.2 Additive across studies, like rule 7 within a study#

This study does not rewrite the Hermes study. Where a Paperclip finding confirms, contradicts or extends a Hermes finding, it is recorded as a cross-study note naming the Hermes batch — so a reader can trace both directions. Cross-study notes are observations, never decisions; the mapping step decides.
