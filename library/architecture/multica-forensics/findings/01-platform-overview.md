## 0. What this batch had to answer

Multica is not a library. It is not a framework. It is a **product**: a hosted web app, a
desktop app, a mobile app, a CLI, and a background daemon that runs on the user's own machine
and drives third-party agent CLIs. CrewAI — the platform we finished last week — was a
Python library you import. Multica is the thing that would have had to be built *around*
CrewAI for CrewAI to be usable by a team.

So the question for batch 01 is: **what is the shape of the machine, and does it already
solve the three poles we are building toward?**

Short answer, measured:

| Pole | Multica's answer | Verdict |
|---|---|---|
| **P1 - the assistant** | A stored `agent` record + an `agent_runtime` row + a per-provider Go adapter | **Real - the strongest finding of this study, and it is tested** (F01-02, F01-03, F01-19) |
| **P2 - the workspace** | `workspace` is the tenant root, fenced by a task-scoped credential | **Real, and it fences the agent's blast radius** (F01-11, F01-12) |
| **P3 - automations** | A literal queue table, a `FOR UPDATE SKIP LOCKED` claim, a distributed cron, an autopilot, and a named failure taxonomy | **Real, and this is exactly the layer CrewAI was measured to lack** (F01-05 ... F01-10) |

Everything in this batch is the *platform* layer. The three pole-specific batches (02, 03, 04)
go deeper; this one establishes that there is something there to go deeper into.

## 2. The data model: the tenant spine

`server/migrations/001_init.up.sql` establishes the whole ontology in one file. Read it as a
sentence: **a workspace has members; members and agents work on issues; issues have comments;
agents take tasks from a queue; daemons keep the connection alive.**

```
workspace --< member (role: owner|admin|member)
    |
    |--< agent --< agent_task_queue -- issue
    |        |
    |        +-- daemon_connection (per agent, status connected|disconnected)
    |
    +--< issue --< comment (author_type: member|agent|system)
             +-- inbox_item (severity)
```

Measured specifics from `001_init.up.sql`:

- **`workspace`** is the tenant root. Every table below it carries `workspace_id UUID NOT NULL
  REFERENCES workspace(id) ON DELETE CASCADE`. There is no unscoped row.
- **`member`** has a `role TEXT CHECK (role IN ('owner','admin','member'))`.
- **`agent`** is a *stored record*, not a process: `runtime_mode CHECK (runtime_mode IN
  ('local','cloud'))`, `status CHECK (status IN ('idle','working','blocked','error','offline'))`,
  `max_concurrent_tasks INT NOT NULL DEFAULT 1`, `owner_id`. An agent is a colleague with a
  concurrency limit.
- **`issue`** carries a **polymorphic assignee**: `assignee_type IN ('member','agent')` +
  `assignee_id`. Also `acceptance_criteria JSONB`, `context_refs JSONB`, and a 7-value status
  CHECK.
- **`comment`** is polymorphic on the author too: `author_type` (member/agent/system).
- **`activity_log`** is polymorphic on the actor: `actor_type IN ('member','agent','system')`.
- **`agent_task_queue`**: `status` in `queued|dispatched|running|completed|failed|cancelled`,
  with `priority INT NOT NULL DEFAULT 0` (`001_init.up.sql:133`). The lease column is **not**
  here - it arrives later, in a two-line migration named for the concept (see section 4.3).

**F01-01 - An agent is a first-class coworker, not a tool.** The polymorphic assignee/author/
actor columns mean the data model refuses to distinguish "a human did this" from "an agent did
this" at the storage layer. Any UI list of "who is on this issue" renders both without a
special case. *Pole: P2, P1. Relevance: Q2 - the workspace pole.*

**144 unique tables** were created across the 598-migration history (measured by counting
distinct `CREATE TABLE` targets). Six migrations contain `DROP TABLE`; eight carry
RETIRED/DEPRECATED markers. The migration history is therefore a **readable archive of what
Multica believed and then stopped believing** - see F01-18.

## 3. The single most important finding: the machine and the teammate are two rows

`server/migrations/004_agent_runtime_loop.up.sql` splits what most systems conflate:

```sql
CREATE TABLE agent_runtime (
    id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    workspace_id UUID NOT NULL REFERENCES workspace(id) ON DELETE CASCADE,
    daemon_id    TEXT,
    name         TEXT NOT NULL,
    runtime_mode TEXT NOT NULL CHECK (runtime_mode IN ('local','cloud')),
    provider     TEXT NOT NULL,
    status       TEXT NOT NULL DEFAULT 'offline' CHECK (status IN ('online','offline')),
    device_info  TEXT NOT NULL DEFAULT '',
    metadata     JSONB NOT NULL DEFAULT '{}',
    last_seen_at TIMESTAMPTZ,
    UNIQUE (workspace_id, daemon_id, provider)
);
ALTER TABLE agent ADD COLUMN runtime_id UUID;
```

(`server/migrations/004_agent_runtime_loop.up.sql:1-18`)

- **`agent_runtime` is the machine.** One row per (workspace, daemon, provider). It holds
  `status` online/offline and `last_seen_at` - the *liveness of a process on someone's laptop*.
- **`agent` is the teammate.** It gains a `runtime_id` FK pointing at the machine that runs it.
- The migration **backfills** `agent_runtime` from the old `agent.runtime_config`, so the split
  was a deliberate refactor of live data, not a greenfield guess.

**F01-02 - Multica separated "the machine that can execute" from "the colleague that is
assigned work."** *Pole: P1, P2. Relevance: Q1, Q2.*

**F01-03 - `UNIQUE (workspace_id, daemon_id, provider)` is the one-tenant-one-engine
primitive.** One daemon produces one runtime row **per provider**. That means: one Hermes
process, one `HERMES_HOME`, one provider bucket - and *many* `agent` rows pointing at it. The
multiplexing primitive we need for one-tenant-one-Hermes already exists here, expressed as a
unique constraint rather than as code. *Pole: P1. Relevance: Q1.*

**F01-04 - The claim is made by the runtime, not by the agent.** `ClaimAgentTask`
(`server/pkg/db/queries/agent.sql:749-808`) selects pending work **for a `runtime_id`**, then
dispatches to the specific agent. One connection, many agents, one lease. *Pole: P1, P3.
Relevance: Q1, Q3.*

## 4. The delivery layer - the thing CrewAI did not have

We closed CrewAI with the verdict *"executor yes, delivery no."* Multica is the control group.
Here is the delivery layer, measured.

### 4.1 A literal queue table

`agent_task_queue` is not an abstraction over a broker. It is a Postgres table with an index
built for the claim:

```sql
CREATE INDEX idx_agent_task_queue_runtime_pending
    ON agent_task_queue (runtime_id, priority DESC, created_at ASC)
    WHERE status IN ('queued','dispatched');
```

(`server/migrations/004_agent_runtime_loop.up.sql:90`)

### 4.2 A real claim

`ClaimAgentTask` - `server/pkg/db/queries/agent.sql:749-808`:

```sql
-- name: ClaimAgentTask :one
... ORDER BY priority DESC, created_at ASC, id ASC
    FOR UPDATE SKIP LOCKED
    LIMIT 1 ...
UPDATE ... SET status = 'dispatched',
    prepare_lease_expires_at = now() + make_interval(secs => @prepare_lease_secs::double precision)
```

**F01-05 - The claim is a genuine work-queue primitive.** `FOR UPDATE SKIP LOCKED` means two
daemons racing for the same queue cannot double-claim; the tie-break `priority DESC, created_at
ASC, id ASC` is total and deterministic (the `id ASC` tiebreak is what makes it a *stable*
order, not a best-effort one); and the claim is a two-step **prepare -> lease** rather than a
bare status flip. *Pole: P3. Relevance: Q3.*

### 4.3 A lease, and the sweepers that reclaim it

`prepare_lease_expires_at` is set at claim time. If the daemon dies mid-prepare, the row is
stranded in `dispatched` forever unless something cleans it. Multica has that something -
`server/cmd/server/runtime_sweeper.go` plus sweepers in `server/internal/service/task.go`,
named in the taxonomy's own header:

> *"emitted by server-side sweepers (`ExpireStaleQueuedTasks`, `FailStaleTasks`,
> `FailTasksForOfflineRuntimes`, `RecoverOrphanedTasksForRuntime`)"*
> - `server/pkg/taskfailure/failure.go:38-41`

The lease column itself was introduced by `server/migrations/124_task_prepare_lease.up.sql`
- a file whose entire contents are two lines:

```sql
ALTER TABLE agent_task_queue
  ADD COLUMN prepare_lease_expires_at TIMESTAMPTZ;
```

A migration named after the *concept* rather than after the ticket is a good sign: someone
intended the lease to be findable.

**F01-06 - A lease without a sweeper is a leak with a good name.** Multica pairs them, and it
names the four sweepers that own the four ways a task can strand: never claimed, claimed and
stalled, runtime went dark, runtime came back with orphans. *Pole: P3. Relevance: Q3.*

### 4.4 A canonical failure taxonomy

`server/pkg/taskfailure/failure.go` is a 346-line package whose header is a small case study
in operational maturity:

> *"until MUL-1949, server/daemon code wrote one of a small handful of coarse failure_reason
> values ("agent_error", "timeout", "runtime_offline", ...). The "agent_error" bucket grew to
> **~30% of all failures** and hid the real cause (provider 401, quota exceeded, context
> overflow, runner crash, etc.) inside the free-form `error` text column."*
> - `server/pkg/taskfailure/failure.go:6-11`

The fix: a typed enum (`type Reason string`, `failure.go:49`) split into **14 platform-side
reasons** (no prefix - the failure is Multica's fault: `queued_expired`, `runtime_offline`,
`runtime_reconnect_timeout`, `timeout`, `iteration_limit`, `agent_blocked`,
`api_invalid_request`, `skill_bundle_unavailable`, `runtime_cli_timeout`,
`environment_prepare_failed`, `invalid_task_identity`, `runtime_access_denied`, ...) and **14
agent-side reasons** with an `agent_error.` prefix, plus `AllReasons()` at `failure.go:342` to
pre-warm the Prometheus label set.

**F01-07 - The failure taxonomy is the observability substrate of a delivery layer.** A queue
without a named failure vocabulary produces dashboards that say "30% failed, reason unknown."
The `agent_error.` prefix is the key design move: it makes "was this the platform's fault or
the agent's fault?" a *string operation* instead of a human reading free text. *Pole: P3.
Relevance: Q3.*

### 4.5 The event contract, and what it deliberately excludes

`server/pkg/eventcontract/events.go` names business facts: `task.queued` (`:20`),
`task.dispatched` (`:21`), and the rest of the task lifecycle. Two lists matter:

```go
// WakeupTypes lists only facts with transactional capture, not every bus event.
var WakeupTypes = []string{...}          // events.go:35
var LifecycleTypes = []string{EventIssueCreated, EventIssueDeleted}   // events.go:46
```

The comment is the finding: **`WakeupTypes` is restricted to facts captured *in the same
transaction* as the state change.** `LifecycleTypes` excludes `issue.created`/`issue.deleted`
because a subscription requires an already-existing issue. This is Multica's answer to
CrewAI's `pending_feedback`: a suspended issue can only be woken by a fact that was recorded
atomically with the thing that would wake it. *Pole: P3. Relevance: Q3.*

## 5. The scheduler: a distributed cron that audits itself

`server/internal/scheduler/` is small in line count and large in idea. It is a
**database-backed distributed cron**: the database is both the lease and the audit log.

**F01-08 - The scheduler's state lives in `sys_cron_executions`, which doubles as its audit
trail.** The unique key is `(job_name, scope_kind, scope_id, plan_time)` - that is the
deduplication primitive: two replicas that both wake at the same `plan_time` for the same
scope cannot both run the same logical execution. A `RunnerID` column makes multi-replica
safety visible in the data rather than implied. `TickInterval` defaults to 30 s.

`JobSpec` (`server/internal/scheduler/spec.go`) carries the full vocabulary an operator
actually needs: `Cadence`, `ScheduleDelay`, `CatchUpMode` (`latest_only` | `every_plan`),
`CatchUpWindow`, `MaxPlansPerTick`, `RunTimeout`, `StaleTimeout`, `HeartbeatInterval`,
`MaxAttempts`, `RetryBackoff`, `AllowStaleReentry`, and a `PlansForScope` hook for arbitrary
cron expressions.

**F01-09 - `CatchUpMode` is the interesting one.** A cron that was down for six hours has a
decision to make: run once now (`latest_only`) or run six times to catch up (`every_plan`).
Multica makes that a per-job, declared choice with a bounded `CatchUpWindow` and
`MaxPlansPerTick`, instead of the usual silent behaviour of "whatever the loop happens to
do." `AllowStaleReentry` is the deliberate escape hatch for jobs that *should* re-enter a
stale execution. *Pole: P3. Relevance: Q3.*

Registered jobs (measured by grepping the registration site): **autopilot, child-done,
issue-wakeup, plugin-hook, search-index, task-usage.** Note that `issue-wakeup` is the
scheduler-side half of the `WakeupTypes` contract in section 4.5.

## 6. Autopilot: a trigger is a row, and a run is a row

`server/migrations/042_autopilot.up.sql` models automation as data, not code:

```
autopilot --< autopilot_trigger (kind: schedule | webhook | api)
    |              +-- cron_expression, timezone, next_run_at
    +--< autopilot_run (status: pending | issue_created | running | skipped | completed | failed)
```

- `autopilot_trigger.kind` covers the three ways an automation can start: **a clock, an inbound
  webhook, or an API call.** `cron_expression` + `timezone` + `next_run_at` mean the schedule
  is stored and inspectable, and the "next run" is a column an operator can query.
- `autopilot_run.concurrency_policy` (`skip` | `queue` | `replace`) is the decision about what
  happens when a run fires while the previous one is still going. This is the classic
  automation bug, expressed as a declared enum.
- `origin_type` / `origin_id` on `issue` close the loop: an issue created by an automation
  knows which automation created it.

**F01-10 - Autopilot is the pole-3 seed, and it is honest about its three triggers.** The
important structural point is that `autopilot_run` is a *separate table* from
`agent_task_queue`: a trigger firing produces a run record, and a run produces queued tasks.
The automation layer and the work layer are not the same layer. *Pole: P3. Relevance: Q3.*

## 7. Tenancy and identity: the fence around the agent

This is the section that speaks directly to our own open hazard.

### 7.1 A task-scoped credential

`server/migrations/108_task_token.up.sql` (ticket **MUL-2600**) introduces a `mat_`-prefixed
short-lived token minted **at claim time**, bound to a `(task_id, agent_id, workspace_id,
user_id)` tuple. The server treats it as **authoritative for actor identity**.

The migration header records the practice it replaced, in its own words: the daemon used to
inject the daemon *owner's* `MULTICA_TOKEN`. That meant an agent process held a credential
with the blast radius of the human who installed the daemon.

**F01-11 - Multica's answer to "how much can an agent do?" is: mint it a credential that names
the exact task it is working on.** The token's binding is the scope. `invalid_task_identity`
is even one of the platform-side failure reasons in section 4.4 - the fence is enforced *and*
observable. *Pole: P2. Relevance: Q2.*

### 7.2 The workspace resolution chain

`server/internal/middleware/workspace.go` - `ResolveWorkspaceIDFromRequest` (`:68`) and
`resolveWorkspaceUUID` (`:113`) implement a documented priority chain:

1. **task-token binding** (`X-Actor-Source == "task_token"`) - *authoritative, and cannot be
   re-negotiated by the client* (`workspace.go:55`, `:106`)
2. middleware context
3. `X-Workspace-Slug` / `?workspace_slug`
4. `X-Workspace-ID` / `?workspace_id` (CLI/daemon compatibility)

**F01-12 - The priority chain is the security boundary, and it is written down as an ordered
list in the source.** The first entry winning is what makes the rest safe: the later headers
are conveniences for humans and CLIs, not negotiation surfaces for an agent process.
*Pole: P2. Relevance: Q2.*

### 7.3 Invocation is fail-closed

`server/internal/service/agent_invocation.go` - `CanMemberInvokeAgent` (`:21`) and
`memberMayInvokeAgent` (`:36`) start from "no" and open up: `agent.PermissionMode !=
"public_to"` short-circuits at `:44`, meaning anything that is not explicitly public is gated
by membership. `ListAgentInvocationTargets` exists so the UI can enumerate who *may* be
invoked rather than discovering it by trying.

**F01-13 - Permission is enumerated, not inferred.** *Pole: P1, P2. Relevance: Q1, Q2.*

## 8. Hermes in Multica - our lane, confirmed

We predicted in the pin that Multica drives Hermes. It does, and the shape is close to ours.

`server/pkg/agent/hermes.go`:

- `hermesACPSubcommand = "acp"` (`hermes.go:144`) - **the backend always launches
  `hermes acp`**. This is the same mandated product lane we arrived at independently.
- `hermesBlockedArgs` (`hermes.go:37`) - a map of flags the daemon hard-codes and that must
  not be overridden by a caller.
- `ParseHermesProfileArgs` (`hermes.go:81`) and `HermesProfileSelection` (`:66`) parse
  `-p/--profile` out of `custom_args`, and the file explicitly says it *mirrors*
  `hermes_cli.main._apply_profile_override` **step 1b**. Multica read Hermes's own CLI
  internals to get the handshake right.
- The file cites **upstream GH #8878** - a known argparse handshake bug - as the reason global
  flags must precede the `acp` subcommand. A vendored workaround for an upstream bug, with
  the bug's URL in a comment, is a maintenance artefact we should copy.
- Per-task **`HERMES_HOME` overlay** via `execenv.ResolveHermesProfile`
  (`server/internal/daemon/execenv/`).

**F01-14 - Multica drives Hermes through `hermes acp`, and it enforces the subcommand rather
than trusting the caller.** *Pole: P1. Relevance: Q1.*

**F01-15 - The profile handshake is mirrored from Hermes's own CLI code, bug-for-bug.** When
you integrate a CLI you do not control, you inherit its argument parser. Multica's response
was to *read the parser* and to record the upstream issue number. *Pole: P1. Relevance: Q1.*

**F01-16 - The ACP machinery is provider-agnostic.** `pkg/agent/` has 77 non-test files, of
which 25 are one-per-provider adapters (`hermes.go`, `claude.go`, `codex.go`, `cursor.go`,
`copilot.go`, `opencode.go`, `openclaw.go`, `pi.go`, `qoder.go`, `qwen.go`, `grok.go`,
`dim.go`, `zeroclaw.go`, `antigravity.go`, `codearts.go`, `codebuddy.go`, `dsh.go`,
`deveco.go`, `kimi.go`, `kiro.go`, `mcode.go`, `omp_session.go`, `qwenpaw.go`, `reasonix.go`,
`traecli.go`). The other ~52 files are **shared**: `acp_session.go`, `acp_terminal.go`,
`acp_usage.go`, `acp_deliverable.go`, `mcp_config.go`, `models.go`, `launch.go`,
`exec_format.go`, `stream_scanner.go`, `thinking.go`. The README claims "26 of them today"
(`README.md:166`) - close to the measured 25, and one provider may hide in a subdirectory.
The correct use of a doc claim is as a checksum, not as the finding.

**F01-19 - Hermes is the second-most-tested provider in the whole package.**
`pkg/agent/hermes_test.go` is **4,860 lines** - behind only `codex_test.go` (6,288) and well
ahead of `models_test.go` (1,914), `kimi_test.go` (1,876) and `opencode_test.go` (1,850).
Multica did not bolt Hermes on as an afterthought; it wrote a test surface for it second only
to Codex. *Pole: P1. Relevance: Q1 - and the single most encouraging signal in this batch,
because it means the Hermes lane in this codebase is exercised, not aspirational.*

**F01-17 - Skills are thin here, and that is itself a measurement.** `server/pkg/skillbundle/`
is ~120 lines; `server/internal/skill/` has `binary.go`, `frontmatter.go`, `reserved.go`; the
built-in bundles are `multica-onboarding` and `multica-platform` in
`server/internal/service/builtin_skills/`. Multica chose to put capability into the *provider*
rather than into its own skill layer. *Pole: P1. Relevance: Q1 - and a caution for us.*

## 9. The migration history is an archive of decisions, not just schema

**F01-18 - 598 up-migrations is the most honest document in this repository.** Six contain
`DROP TABLE`; eight carry RETIRED/DEPRECATED markers. The one to read first:

`server/migrations/344_plugin_v2_reset.up.sql` dropped **14 plugin tables** wholesale plus 11
triggers and functions - and stated the reason *in the migration itself*: the system "never
left its feature flag, holds no production data." It then described the replacement: **one
`plugin_installation` row + `plugin_storage` + `plugin_secret`.**

That is rule 10 executed properly by someone else: a whole subsystem deleted, with the reason
and the successor written into the artefact that performs the deletion. We should copy the
*practice*, not the schema. *Pole: P3. Relevance: Q3.*

The rest of the archive, measured: `042_autopilot` (the P3 seed), `004_agent_runtime_loop`
(the machine/teammate split), `108_task_token` (the fence), and `005_daemon_pairing` with
`029_drop_daemon_pairing` - a subsystem added and then removed, a pairing model that did not
survive contact with reality. A repository that deletes things on the record is a repository
we can trust to have measured what it kept.

## 11. What is NOT here (yet)

Measured absences, stated as absences and not as judgements:

- **No per-tenant Hermes home in this codebase.** `agent_runtime` is unique per
  `(workspace_id, daemon_id, provider)`, and `HERMES_HOME` is resolved per *task* through
  `execenv`. The tenancy-of-the-engine question is answered at the *daemon* level (one daemon
  per workspace, by the unique constraint), not at the *home* level. Our CC-84 hazard is
  therefore **not** solved by copying this shape - it is *narrowed*, because the agent's
  credential is task-scoped (section 7.1) even though the engine is shared.
- **No scheduler-side multi-tenancy abstraction read.** `sys_cron_executions` is scoped by
  `(job_name, scope_kind, scope_id, plan_time)`, and `scope_kind`/`scope_id` is the tenancy
  hook - but batch 01 did not read the scoping implementation. **Deferred to batch 03.**
- **No verified shared-engine-per-workspace *deployment*.** The unique constraint makes one
  runtime per (workspace, daemon, provider) a database fact. Whether Multica actually *runs*
  one Hermes process per workspace in production, or many workspaces against one daemon, is
  not visible from the schema. **Deferred to batch 02** - `internal/daemon/` is where the
  answer lives.
- **Route count.** See section 12 - measured now, but the *shape* of the API surface is a
  batch-02 question.

## 12. The route count, measured properly

The pin flagged this as unresolved. It is now measured, with the method stated so the number
can be defended or refuted.

**Method:** grep for HTTP verb registrations in the one file that owns the router,
`server/cmd/server/router.go` (2,717 lines). Routes are registered against
`publicapiv1.Path*` constants rather than inline literals, which is why earlier attempts that
matched inline strings returned 19, then 58, then 1,175 - all three were measuring the wrong
thing.

**Result: 469 route registrations** - 185 `GET`, 176 `POST`, 56 `DELETE`, 31 `PUT`,
21 `PATCH`.

**Cross-check:** a repo-wide grep for verb registrations outside `router.go` returned 339
hits, **all of them in `cmd/multica/`** - that is the CLI acting as an HTTP *client*
(`responseHeaders.Get(...)`, `r.URL.Query().Get("token")`), not a server registering routes.
So 469 is the defensible count for the server's route table, and the 339 are a separate
population (the CLI's outbound calls) that must not be added to it.

**Caveat carried forward:** 469 counts *registration lines*. Some are group registrations
(`r.With(authRL).Post("/auth/send-code", ...)`) and some may share a handler. The number is a
size signal, not an endpoint inventory. Batch 02 will produce the inventory if it is needed.
