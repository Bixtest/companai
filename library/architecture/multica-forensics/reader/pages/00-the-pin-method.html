Multica Study — Batch 00: the pin, the method, and what this study is#

Folder: library/architecture/multica-forensics/ · Status: OPEN — begun 2026-10-15 This is a clean forensic study, run the same way as library/hermes-forensics/, library/architecture/paperclip-forensics/ and library/architecture/crewai-forensics/. It reads ONE source tree, measures it, and verifies every load-bearing claim against the source code. Nothing from any earlier study is reused, referenced, or assumed — Multica is read on its own terms.

Why this platform is third. The owner's ruling was "one platform at a time": Paperclip first (9ae258f/97b4dfc/2bef78d/f1e5dea), CrewAI second (dcd4675→d81c86e), Multica third. The first two sat at opposite ends of one question — Paperclip is a company/task-runner, CrewAI is an agent framework. Multica is the first platform studied that appears to be aimed at the same target we are: it describes itself as a workspace where humans and AI agents work on one board, with agents as first-class teammates, runtimes, runs, squads, workspaces and roles. That makes it the sharpest candidate yet — and the most dangerous one to read casually, because similarity invites the assumption that it is already the thing we want. Per the method, the code decides, not the landing page.

1.1 The identity limit (stated, not glossed)#

There is no .git, so the exact upstream commit cannot be read from the tree. Unlike CrewAI (which carried 1.15.28 and a matching docs tree), Multica carries 0.2.0 — a young version number on a very large tree (see §2), which is itself a signal to interpret carefully: the package.json version describes the frontend workspace, and the product is released "most weekdays" per the README, so main is a fast-moving snapshot. The identity we can assert is: source of Multica, version string 0.2.0, extracted 2026-10-15 17:53, zip md5 30ddc64af536212e25a6c00db5672b82. A reader reproducing this study must match those. Any claim here about "the latest Multica" is a claim about this extract.

Date clue: the docs content is monorepo-versioned (no per-release doc trees like CrewAI), so the strongest anchor is the zip md5 plus the extracted date. Where a batch needs to know "is this current", it says so explicitly rather than assuming.

2.5 Agent-facing assets#

AGENTS.md (12,811 B) is present at the root, plus CLAUDE.md (11 B — a pointer), plus per-app apps/mobile/AGENTS.md. AGENTS.md states binding rules for AI coding agents working in the repo — package boundaries (views → core + ui), state rules (TanStack Query vs Zustand), database rules that forbid foreign keys and cascading deletes, concurrent-index migration rules, and UUID-source rules. This is the same posture Paperclip and CrewAI had (built to be worked on by agents) and is itself a finding — it belongs in PZ, and §3 of it (the DB rules) is exactly the kind of hard-won convention our own project keeps relearning (cf. rule 9a, rule 10d).

2.6 What is NOT here (named now, to guard the reading)#

  • No .git — identity is the zip (§1.1).
  • No per-release doc trees (unlike CrewAI's 45 × 4) — the docs are monorepo-versioned; they are a small surface and can be read whole, but are still claims.
  • The mobile/ app is excluded from root build/typecheck/test scripts (--filter=!@multica/mobile) — a later batch must not assume mobile is covered by the root gates.
  • node_modules is absent (correct); go.sum/pnpm-lock.yaml are present, so dependency identity is readable.

3. The method (how every batch is produced)#

The method is inherited verbatim from the Hermes, Paperclip and CrewAI studies (rules 1–10), with the pole frame (§3.1) and the additive-across-studies rule (§3.2) as before.

  1. Docs are claims; code is the authority. Here the docs are small and persuasive — the README describes our own vision back to us. That is precisely when rule 1 matters most. Every load-bearing statement is checked against the source. Where they disagree, the code wins and the disagreement is recorded.
  2. Every number is measured at the time of writing, never carried from memory or an older document.
  3. Claims carry their evidence: a line resting on code cites the file and line it was read at.
  4. Two value questions per capability: Q1 · USER VALUE (how it serves a person using the platform) and Q2 · VISION VALUE (how it serves the AI-first business & resources planner vision, incl. versatility and integratability).
  5. No comparison to our own platform inside the batches. The cross-platform mapping is a separate later pass.
  6. Every capability is named, including ones we will not use. Nothing is silently dropped.
  7. Findings are additive and never overwrite history.
  8. Plain words — every capability gets a one-sentence plain gloss before any detail.
  9. THE POLE FRAME. Every finding is tagged P1 / P2 / P3 / PX-W / PX-F / PZ.
  10. The retirement rule (C13-14). Before reusing any setting/key/module named in an older document or another platform's doc, search that platform's migrations/config for a retirement entry. With 1,196 migration files, Multica is the richest retirement surface studied so far — a silently-removed feature is the most valuable kind of finding, and here it is findable.

3.1 The pole frame — the three poles, defined once#

Tag Pole The owner's words (abridged)
P1 The aissistant (the AI user / agent) versatile, integratable, rich featured architecture in itself, deployable in different contexts (workspaces, automations, later the studio)
P2 The workspace highly functional, versatile, integratable, rich featured, adaptable to the mix of current and future features, use-cases and needs
P3 Automations where agents work on assigned tasks, assign tasks, etc. Paperclip is a blueprint
PX-W Widgets architecture cross-cutting: the composable UI surface
PX-F Frontend wiring & construction cross-cutting: how the surface is built and wired

Plus one escape hatch (PZ): "any other findings you identify there that can fit our vision, project, architecture, or a potential use case or added value for the end user." Tagged PZ with a one-line reason for keeping them.

3.2 Additive across studies, like rule 7 within a study#

This study does not rewrite the Hermes, Paperclip or CrewAI studies. Where a Multica finding confirms, contradicts or extends an earlier finding, it is recorded as a cross-study note naming the earlier batch — so a reader can trace both directions. Cross-study notes are observations, never decisions.

4. The batch plan (each documented as it is completed)#

Findings are organised per pole, one file per pole, plus an overview and a synthesis. Multica is a multi-surface product (Go server + daemon + web/desktop/mobile), so the pole weighting will differ from both earlier studies — but the structure is identical so the later mapping is a per-pole join.

# Batch / File Pole What it answers
00 This file — pin and method — task zero + method + pole frame
01 findings/01-platform-overview.md — What is Multica? the workspace/issue/agent/run model, the Go backend, the daemon, the control plane
02 findings/02-the-aissistant.md P1 what an "agent" is here: provider + runtime + config, skills, permissions/access scopes, the agent record
03 findings/03-the-workspace.md P2 workspaces, members/roles, projects, repos/Git, issues, the data model (from migrations)
04 findings/04-automations.md P3 the scheduler, dispatch, autopilots, runs, retries, wakeups, delegated recovery — the delivery layer
05 findings/05-widgets-and-frontend.md PX-W / PX-F the UI: packages/ui + packages/views, token discipline, the desktop/mobile surfaces, the widget model
06 findings/06-out-of-pole.md PZ everything else that fits our vision (security model, tenancy, telemetry, plugins, MCP, channels, docs practice)
07 findings/07-SYNTHESIS.md all what Multica teaches each pole; ranking; the bridge to Hermes/Paperclip/CrewAI is a LATER pass

Each batch document carries: (a) what was read and its measured size; (b) a capability table tagged by pole with Q1 · Q2; (c) the code verification with file:line evidence and any doc-vs-code divergence; (d) findings carried forward.

A note on the pole weighting, stated up front. Multica is the first platform studied whose stated purpose is the same as ours, so the temptation to score it as "already done" is highest here. The batches answer the three value questions in the opposite direction too: not only "does it fit our poles" but "where does it draw its boundaries, and are they ours?" — because a close neighbour is the hardest to reuse and the easiest to copy badly. That question is answered in the batch notes and ranked in batch 07, never assumed.

5. Ground rules restated as a checklist the reader can hold this study to#

  • Is the claim measured, or remembered? → must be measured.
  • Does the line rest on a doc, or on code? → code, always — and because Multica's docs describe our own vision back to us, this is enforced hardest here.
  • If doc and code disagree, is the disagreement recorded? → must be.
  • Is every capability named, including the ones we will not use? → must be.
  • Is every finding tagged with its pole (P1/P2/P3/PX-W/PX-F/PZ)? → must be.
  • Are the two value questions answered in the owner's words? → yes, per capability.
  • Is there any comparison to our own platform in a batch? → must be none; that is the later mapping pass.
  • Before reusing an older-doc setting, was the retirement rule run (rule 10)? → must be — and with 1,196 migrations, this is checked hard.
