Zulip Study — Batch 00: the pin, the method, and what this study is#

Folder: library/architecture/zulip-forensics/ · Status: OPEN — begun 2026-10-16 This is a clean forensic study, run the same way as hermes-forensics/, paperclip-forensics/, crewai-forensics/, multica-forensics/, gastown-forensics/, n8n-forensics/, buzz-forensics/ and openrig-forensics/. It reads ONE source tree, measures it, and verifies every load-bearing claim against the source code. Nothing from any earlier study is reused, referenced, or assumed — Zulip is read on its own terms.

Why this platform is ninth. The owner's ruling was "one platform at a time". Eight are closed: Hermes, Paperclip, CrewAI, Multica, Gas Town, n8n, buzz, openrig. The owner's own platforms/references.md names the remaining two in order — mattermost, zulip — and the owner chose zulip as the ninth.

Zulip is the first platform in this study that is a mature, decade-old, production chat product run by thousands of organisations (the README claims "over 1,500 contributors"). Where buzz was a young reimplementation of team chat on Nostr, Zulip is the real thing — 19 years of design decisions, a hosted-service business behind it, and a documentation body large enough to measure against the code. It is also the first platform whose tenancy model is a first-class, separately-documented subsystem (docs/subsystems/realms.md), which makes it the strongest P2 counterweight the study has yet seen to openrig's no-tenancy.

The owner's directive carried into this study (from the n8n, buzz and openrig briefs, still in force): identify what fits the vision and what could be taken further. Per the method, the batches stay comparison-free — the "take it further" notes are observations in the synthesis, and the decisions stay the owner's at the mapping pass.

1.1 The identity limit (stated, not glossed)#

There is no .git, so the exact upstream commit cannot be read from the tree. What is readable is version.py's ZULIP_VERSION = "12.0-dev+git" — a main-branch development string, not a tagged release — beside LATEST_RELEASE_VERSION = "12.3" and LATEST_MAJOR_VERSION = "12.0". version.py tries to read a zulip-git-version file that does not exist in the extract (it is generated at build time), so the commit hash is unavailable. Any claim here about "the latest Zulip" is a claim about this extract, at 12.0-dev+git (the 12.x line, past the 12.3 release).

⚠️ The one version trap in this tree. version.py also carries three compatibility constants that are NOT the version of this tree: DESKTOP_MINIMUM_VERSION = "5.4.3" and DESKTOP_WARNING_VERSION = "5.9.3" are the desktop-app gates (a different product line, zulip-desktop, versioned independently), and API_FEATURE_LEVEL = 513 is a monotonic API counter, not a release number. A later reader must not read 5.4.3 or 513 as the study's pin. The pin is 12.0-dev+git; the others are contract constants.

1.2 The seven missing files — measured, named, and dismissed as inert (a pin finding)#

The extraction did not silently truncate: every file was attempted and the failures enumerated. 7 of 9,016 files (0.08%) could not be written because their absolute paths exceed 260 characters on Windows. All 7 are test fixtures for the Mattermost data-importer — binary assets used to exercise an import tool, not any part of Zulip's own architecture:

File Type
.../mattermost_fixtures/.../harry-ron.jpg image
.../mattermost_fixtures/.../this is a file binary blob
.../mattermost_v11.1.0_fixtures/.../Recording 2026-01-19 203522.mp4 video
.../mattermost_v11.1.0_fixtures/.../Screenshot 2025-12-19 210913.png image
.../mattermost_v11.1.0_fixtures/.../text file.txt text
.../mattermost_v11.6.0_fixtures/.../Screenshot 2026-03-10 210730.png image (×2)

Why this does not weaken the study. (1) They are fixtures, not source — no .py, .ts, .md or config file is missing. (2) They belong to data_import/, which the pin does not study. (3) The fixture directory tree extracted intact, so the parent structure (which reveals how the importer works) is present. Rule 1 is satisfied: the absence is stated, not hidden; 13 of the 14 long paths are directories or these fixtures, and the study does not depend on any of them. The one honest consequence: any future claim of the form "the Mattermost importer accepts file X" cannot cite this extract for byte-exact fixture content.

2.3 The rule-1 caution — a count that lied, caught in the pin#

The first pass at "how much Python is there" produced 13,952 lines via find … | xargs wc -l | tail -1. That number is wrong by 30×. xargs split the 2,037 filenames into multiple wc invocations, and tail -1 showed only the last batch's total. The honest measurement is a walk that sums per-file: 425,702. This is the same failure mode that memory already records for grep -c $'\r' — a shell pipeline quietly reporting a subset. The corrected number is used everywhere in this study.

2.4 The three "architecture docs" that matter (rule 1 — a claim is a claim)#

Zulip ships 249,760 words of contributor documentation across 182 markdown files, of which the docs/subsystems/ directory holds 35 named subsystem documents — realms.md (the tenancy model), queuing.md, events-system.md, sending-messages.md, database-concurrency.md, caching.md, widgets.md, schema-migrations.md and more. This is the richest first-party documentation body in the study (n8n shipped 45 pages × 5 languages; Zulip ships a whole contributor manual). Per rule 1, none of it is accepted as truth — every claim is traced to code — but its existence, and the fact that it names subsystems, is itself a finding about how this project thinks about its own architecture.

3. The three poles — the frame for every batch (carried from the workshop)#

  1. P1 — the aissistant. How does a conversation with a machine happen? Agents, bots, tool-calls, the seam between the platform and the model.
  2. P2 — the workspace. How is a tenant represented? What is the container, the membership model, the permission surface? This is Zulip's strongest documented pole (realm).
  3. P3 — automations. How does something run without a human? Schedulers, queues, webhooks, outgoing bots, the delivery guarantee.

Plus the cross-cutting lenses: PX-W (the widget/composition surface) and PX-F (the frontend architecture), and PZ (the out-of-pole escape hatch — security, tooling, the verification culture).

4. The method (inherited, binding — from `library/development/WORKING-RULES.md`)#

  • Rule 1 — docs are claims, code is the authority. Count FIRST (rule 0b).
  • Rule 5 — no comparison to our own platform inside a batch. Comparisons are the synthesis' job, and even there they are observations, not decisions.
  • Rule 6 — name every capability. A mechanism without a name cannot be discussed.
  • Rule 9 — pole-tag everything (P1/P2/P3/PX-W/PX-F/PZ).
  • Rule 10 — the retirement rule. What was built, then removed, is the most honest evidence.
  • Rule 13 — never let a number stand unverified. Re-measure before citing.
  • Never git add -A. Plain-English reporting; never end on "your call".
