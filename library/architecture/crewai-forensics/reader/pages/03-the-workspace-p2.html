BATCH 03 VISUAL GUIDE — POLE 2

The workspace: a folder that binds text to code by name

How a directory of YAML describes a team, how strings become live objects, and where the folder model stops short of a container of records

Batch 03 — Pole 2: the workspace#

Pole: P2 — the workspace. The container where the work lives: projects, the units of organisation, files, knowledge, and the surface a user operates. Status: read from lib/**/*.py only. Every claim carries file:line.

0. In plain words — where does a CrewAI "workspace" live?#

CrewAI has no server-side workspace. What it has is a project folder on your disk, generated by a command, whose contents are plain text:

  • agents.yaml — the team, written as data (each entry is a role/goal/backstory with {variables});
  • tasks.yaml — the work, written as data (each entry names the agent that does it);
  • crew.py — a small Python file that binds the two together with decorators;
  • main.py — a command file with verbs (run, train, replay, test, run_with_trigger);
  • tools/ — your custom tools; knowledge/ — documents; skills/ — SKILL.md packs.

Then crewai create crew <name> scaffolds that folder, and crewai deploy zips it and posts it to CrewAI's cloud. So "the workspace" in CrewAI is a git-friendly directory plus a deployment story — not a database, not a tenant, not a UI. The interesting engineering is in how the YAML and the Python are reconciled, and in how files are handled; both are worth taking.

2. The project template — a workspace as a folder#

create_folder_structure (create_crew.py:48) is the scaffolder's core, and it is unusually careful about naming — it validates a project name against Python's own rules before creating anything:

text 
create_crew.py:59    folder_name = name.replace(" ", "_").replace("-", "_").lower()
create_crew.py:72    if folder_name[0].isdigit():  raise ValueError(...)
create_crew.py:77    if keyword.iskeyword(folder_name):  raise ValueError(...)
create_crew.py:82    if not folder_name.isidentifier():  raise ValueError(...)
create_crew.py:88    if folder_name in reserved_names:  raise ValueError(...)
create_crew.py:95    class_name = name.replace(...).title().replace(" ", "")

and then creates a fixed layout (:148-155):

text 
create_crew.py:148   folder_path.mkdir(parents=True)
create_crew.py:149   (folder_path / "tests").mkdir(exist_ok=True)
create_crew.py:150   (folder_path / "knowledge").mkdir(exist_ok=True)
create_crew.py:152   (folder_path / "src" / folder_name).mkdir(parents=True)
create_crew.py:153   (folder_path / "src" / folder_name / "tools").mkdir(parents=True)
create_crew.py:154   (folder_path / "src" / folder_name / "config").mkdir(parents=True)
create_crew.py:155   copy_assistant_instructions(folder_path)   # writes AGENTS.md/CLAUDE.md/…

Every rejection is a named error, not a crash — a digit-leading name, a Python keyword, a name that is not an identifier, a reserved script name. This is the kind of validation our own "create a workspace" flow should have, and it costs nothing to copy.

2.1 The template is a *working example*, not an empty skeleton#

templates/crew/ ships config/agents.yaml, config/tasks.yaml, crew.py, main.py, pyproject.toml, README.md, knowledge/user_preference.txt, skills/, and tools/custom_tool.py. The agent YAML is a real two-agent crew:

yaml 
# templates/crew/config/agents.yaml
researcher:
  role: >
    {topic} Senior Data Researcher
  goal: >
    Uncover cutting-edge developments in {topic}
  backstory: >
    You're a seasoned researcher with a knack for uncovering the latest
    developments in {topic}. ...

Plain meaning: the shape of a workspace is config-as-data with {placeholder} variables, and the template proves the shape by being runnable. There is also a parallel templates/crew/json_crew/ and templates/declarative_flow/flow.yaml — i.e. CrewAI ships three project flavours: decorator-Python, JSON, and declarative-YAML flow.

2.2 `main.py` is the "workspace verbs" surface#

The generated main.py defines exactly five verbs, and they are the vocabulary of a runnable workspace: run(), train(), replay(), test(), run_with_trigger(). run_with_trigger is the interesting one — it takes a JSON payload on argv, wraps it as crewai_trigger_payload, and kicks off:

python 
trigger_payload = json.loads(sys.argv[1])
inputs = {"crewai_trigger_payload": trigger_payload, "topic": "", "current_year": ""}
result = {{crew_name}}().crew().kickoff(inputs=inputs)

Plain meaning: CrewAI's workspace has a built-in idea of being triggered by an external event with a JSON payload — which is precisely our P3 (automations) seam, surfaced in the P2 file.

3. The binding: how YAML meets Python#

The @CrewBase decorator (project/crew_base.py:814, metaclass _CrewBaseType) turns an ordinary class into a crew definition. The decorators that mark its methods are tiny and uniform (project/annotations.py): @agent (:78), @task (:66), @llm (:90), before_kickoff (:42), after_kickoff (:54) — each simply wraps the method in a typed marker object and memoises it (annotations.py:75,87,99).

At construction time the framework:

  1. resolves the config paths and base directory (crew_base.py:135, :147);
  2. loads the two YAML files into agents_config / tasks_config (load_configurations, :368; _load_config, :337; load_yaml, :378);
  3. maps YAML string references to live objects — map_all_agent_variables (:621) and map_all_task_variables (:689).

The mapping is the clever part (_map_agent_variables, :643). A YAML entry may name an llm, a tools list, a cache_handler, or a step_callback as a string; the mapper looks the name up among the class's marked methods and calls it:

text 
crew_base.py:663   if llm := agent_info.get("llm"):
crew_base.py:664       factory = llms.get(llm)
crew_base.py:665       self.agents_config[agent_name]["llm"] = factory() if factory else llm
crew_base.py:667   if tools := agent_info.get("tools"):
crew_base.py:669       self.agents_config[agent_name]["tools"] = [tool_functions[tool]() for tool in tools]

Plain meaning: the YAML is not a second source of truth that can drift — it is a reference by name into the Python class. llm: my_llm in YAML becomes whatever @llm def my_llm() returns. If the name is not found, the string is kept as-is (:665), which is how a raw model name can appear directly in the YAML. This is a typed string-reference resolution pattern, and it is a cleaner answer to "config vs code" than either duplicating values or code-generating them.

Both crew.py (decorators) and json_loader.py (JSONCrewProject, :158) resolve to the same CrewDefinition model (project/crew_definition.py:297) — one definition, three authoring syntaxes.

4. Files — a first-class subsystem, not an afterthought#

crewai-files is a separate package (33 files / 8,165 lines) for one reason: a file must be delivered to a model differently depending on which model you use. The structure shows it plainly:

text 
core/        types.py (ImageFile, PDFFile, TextFile, AudioFile), sources.py, resolved.py
processing/  constraints.py, transformers.py, validators.py, enums.py
formatting/  anthropic.py, bedrock.py, gemini.py, openai.py, api.py
uploaders/   anthropic.py, bedrock.py, gemini.py, openai.py, base.py, factory.py
resolution/  resolver.py
cache/       upload_cache.py, cleanup.py, metrics.py
  • FileMode = Literal["strict", "auto", "warn", "chunk"] (core/types.py:67) — four policies for how to handle a file a provider cannot accept directly (e.g. chunk it, warn, or refuse).
  • _FileSourceCoercer (core/types.py:28) accepts a str (path or URL), a Path, bytes, or a stream, and coerces it into one of FilePath / FileUrl / FileBytes / FileStream (:32-46).
  • FileUploader (uploaders/base.py:31) is the provider contract: provider_name (:39) and upload(file, purpose) -> UploadResult (:43), where UploadResult (:13) carries file_id, provider, content_type, file_uri, expires_at.
  • upload_cache.py caches uploads by content hash with a TTL and a max entry count, so the same file is not re-uploaded to the same provider twice (cache/upload_cache.py).

Plain meaning: this is the pattern to copy when files enter an AI system: model the source, the constraints, the per-provider format, and the cache as four separate things, and let a factory choose the uploader. The expires_at on an upload is a detail our platform will otherwise forget.

5. Knowledge — the readable content substrate#

Knowledge (knowledge/knowledge.py:88) is a BaseModel that owns sources and an embedder, and exposes three methods: query(...) (:135), add_sources() (:154), reset() (:162). Ten source types ship in knowledge/source/:

text 
base_knowledge_source.py · base_file_knowledge_source.py
text_file · pdf · csv · excel · json · string · crew_docling (documents via Docling)

Plain meaning: "knowledge" is a known document set attached to an agent or a crew, queried by similarity — deliberately simpler than memory (which is written during the run; knowledge is added before it). The collection_name on an agent's knowledge defaults to its role (agent/core.py:587), which is a neat but implicit tenancy key — worth noting and not worth copying blindly (roles are not unique).

6. MCP transports — the workspace's tool-server door#

mcp/transports/ contains exactly four files: base.py, stdio.py, http.py, sse.py. Three transports, one base. Combined with the config models of Batch 02 (MCPServerStdio / MCPServerHTTP / MCPServerSSE), the picture is complete: CrewAI treats "an external tool server" as a configured endpoint with a transport, an optional credential header, and an optional tool filter.

Plain meaning: the MCP layer is small, complete and boring on purpose — which is what a transport seam should be. Our own lib/hermes-gateway-transport.ts seam is the same idea, and this batch confirms the shape is standard.

7. Deploy — the workspace's other half#

lib/cli/src/crewai_cli/deploy/ is 2,287 lines: validate.py (1,206), main.py (913), archive.py (168). DeployCommand (deploy/main.py:274) is a BaseCommand + PlusAPIMixin — i.e. it talks to CrewAI's own cloud ("Plus" API). Before deploying it:

  • refuses on a running comparison (_refuse_on_running_comparison, :193);
  • requires a lockfile (_needs_lockfile_for_deploy, :225; _ensure_lockfile_for_deploy, :233);
  • runs predeploy validation (_run_predeploy_validation, :31);
  • prepares the project (_prepare_project_for_deploy, :252) and archives it (archive.py).

Plain meaning: CrewAI's answer to "where does this live?" is a zip of the folder, shipped to their cloud, with a validation gate in front. That is a hosted-service answer, not a workspace-as-data answer. It is also the clearest place where our platform's needs diverge from CrewAI's — recorded as a divergence below, not as a finding to copy.

Reading the table. 3.2, 3.4 and 3.7 are the three things worth carrying into our SRS. 3.2 is cheap and improves every future "create" flow. 3.4 is the cleanest answer we have seen to the config-vs-code tension that has already cost this project rework. 3.7 is a complete file model, and files entering an AI system is certain to be needed. 3.12 is the honest gap: CrewAI's workspace is a folder of descriptions, and our workspace must be a container of records — the two are not the same object and must not be conflated in the mapping pass.

9. Doc-vs-code divergences recorded ⚠️ FINDING NOTE#

  1. The docs say "workspace"; the code has a folder. There is no workspace entity, no workspace id and no workspace-level permission anywhere in lib/**. Anything a reader infers about a shared or multi-user workspace is not in the code.
  2. agents.yaml config paths are optional and fail soft. _load_config logs a warning and returns {} when the file is missing (crew_base.py:354-359), so a mis-named config file produces an empty crew, not an error — a silent-failure path of exactly the kind this project has been burnt by.
  3. Knowledge collection name defaults to the agent's role (agent/core.py:587). Roles are not unique, so two agents with the same role share a knowledge collection. Not documented as a hazard.
  4. deploy requires a lockfile, so deploying a project without one fails at a step the docs present as optional (deploy/main.py:225).

10. Carried forward#

  • Batch 04 (P3 automations) will take the two threads this batch opened: 3.6 (run_with_trigger, the JSON-payload door into a crew) and the Flow engine's durability, and test whether CrewAI has a real notion of a task arriving and being scheduled.
  • The gap recorded in 3.12 becomes a standing question for the mapping pass: CrewAI's folder and our record-store workspace are different objects; the mapping must say which CrewAI ideas survive the change of substrate.
  • 3.4 (string-reference resolution) is a candidate pattern for our own config-vs-code problem; note it for the SRS, and do not resolve it here.
