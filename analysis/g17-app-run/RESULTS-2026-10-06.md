## The order that made the result unambiguous

The model was probed from OUTSIDE the platform FIRST
(`outside-probe-2026-10-06.md` — PASS, http=200, 32s, correct IR). The owner set that order
deliberately: if the platform test then failed, the fault would be the platform's, not the
model's. Both halves passed, so there is no ambiguity to unpick.

## What went wrong on the way, and how it was caught

**First attempt: login http=401 "Invalid email or password".** This was NOT a platform fault and
NOT a defect — it was a wrong password in the test script. The script had guessed `secret` for
superadmin; the container seeds superadmin with `OM_INIT_SUPERADMIN_PASSWORD=password`
(measured from the running container's env). Re-run with `password` -> http=200.

Also caught before it could waste a cycle: the run-object route's real body contract is
`{agent, messages:[{role,content}]}` (read from `api/ai/run-object/route.ts`,
`runObjectRequestSchema`), NOT `{agentId, input}`. The script had it wrong; both route paths were
then confirmed against the generated table (`api-routes.generated.ts` line 32 `/auth/login`,
line 239 `/ai_assistant/ai/run-object`) instead of guessed.

## The container rebuild that made it possible

The running container had no bind mount and a baked image, so the agent declaration reached disk
but not the app. Rebuilt: `docker compose -f docker-compose.fullapp.yml build app`, **12m22s**,
new image `open-mercato/app:local` id `cd8c4242dcc0`. Container recreated on it.

Measured before -> after, same file `/app/apps/mercato/.mercato/generated/ai-agents.generated.ts`:

- before: **0** occurrences of `ai_assistant`
- after:  **5** - line 2 imports `@open-mercato/ai-assistant/modules/ai_assistant/ai-agents`,
  line 10 `moduleId: "ai_assistant"`.

## What this does and does not establish

**Establishes:** the platform path works end to end. Auth -> the app's registry resolves the IR
agent -> policy check passes -> the model is called from inside the app -> a schema-valid IR
object comes back over HTTP. G-17's decisive loop has a working right-hand side.

**Does NOT establish:** answer QUALITY. The owner explicitly deferred that ("what matters now is
to get the right response, not the quality of it") - model comparison and commercial
OpenAI/Claude APIs are later work. This run asserts request-shape correctness and pipeline
liveness, nothing about how good the query is.

**Latency note (not a defect):** 69s in-platform vs 32s for the same prompt straight to the
model. The delta is the 530-token system prompt the platform injects plus platform overhead.
A data point for the later latency budget.

**Field-name note (not a discrepancy):** in-platform returns `grain`/`created_at`; the raw
outside probe returned `dimensions`/`date`. The platform's schema is doing its job - different
surface, same intent. Not to be chased.
